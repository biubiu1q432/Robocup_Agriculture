总运行逻辑：
    车的运动靠背地图，每一段距离都是走死的；
    机械臂的动作组也是提前调定，到时直接调用
    机械臂的运动决策靠视觉采集的信息：
        已知，机械臂的两爪对应的蔬菜状态有9种(成熟、未成熟、没有蔬菜，然后3X3得到共9种)
        故可以直接全枚举所有情况的蔬菜状态再进行机械臂状态调用，抓取逻辑仅此而已
    故第一个关键点（或者说是理论构建上的第一个关键点）在于视觉，如何准确识别出蔬菜的状态，只需要这个，理论上就能结束比赛了
    注意到蔬菜状态跟其颜色强绑定，且这一个因素足以作为决定性因素，故使用传统视觉进行颜色过滤作为解决方案，问题算是基本解决了
    至于还有一个需求，就是通过网络告知大车开始运动和告知大车已经完成当前区域的抓取（农业采摘用了两台机器人，且假设了现场只能打开一台机器人的开关）；
    这个用Socket网络编程就行，问题不大
    
    以上是大致理论分析思路，但是实际测试实现效果的时候出现了以下的现实问题：
        1、抓取和识别的时间差，需要做到识别成功后抓取
        2、颜色的色域是真的难调。。
        3、实际让机器人走路的时候还是会有向某方向偏移的现象，就是走着走着突然走偏了，
            虽然是一个很小的偏角，但是一直走下去会累计误差会导致小车彻底走偏，直接game over

main.py:
    全局变量 - 便于配置：
        Option - 通讯桥的串口配置信息
        colors - 颜色过滤时想要保留的颜色的hsv色域，给__monitor()用 —— 是手调的
        filtered_colors - 颜色过滤时想要去掉的颜色的hsv色域，给__monitor()用 —— 是手调的
        colorNames - 想要保留的颜色的名称，打印结果用，下标与colors中的颜色一一对应
        check_corrected_colors - 给__align_monitor()用的colors（因为之前的__align_monitor旧版本废案需要检测跟colors不一样的颜色，所以单独列出）
        check_corrected_filtered_colors - 给__align_monitor()filtered_colors
        rois - 蔬菜落在原始图像上的大概位置，用这个来进行ROIS的切割 - 是手调的
        roiNames - 每个ROI的名称，下标跟rois一一对应

    Robot类：
        机器人的主体功能类，通过调用其他主要功能文件中的模块进行运转
        __init__() - 机器人类内各种成员变量的初始化
            包括：
                功能部件：
                    arm_bridge - 机械臂通讯桥，用于树莓派与机械臂之间的单向串口通信
                    car_bridge - 底盘通讯桥，用于树莓派与机械臂之间的双向串口通信
                    socket_client - socket通信用的接口，用于主动机器人与从动机器人之间的通信
                    camera - 抽象出来的摄像头类，用于操作视觉相关的功能
                常量：
                    __big_step - 上一对蔬菜和下一对蔬菜之间的间距
                    __side_step - 用于小车莫名其妙偏移时侧向调正的距离
                其他：
                    __decisions - 机器人对于不同蔬菜情况下的决策集合，在机器人遇到不同的蔬菜情况时从中选取指定情况进行调用
                                    action表示进行什么函数
                                    args表示向该函数传递什么参数
                                    time表示该动作持续的时间，即 为该动作的进行 延时阻塞其他行为的时间
                    monitor_round_cnt - 用来给拍摄的图像进行编号用的，无重要功能

        init() - 机器人类内对各个作为功能部件的成员变量的进一步配置
            包括：
                各类通讯部件的属性配置、各类信息接收线程的启动；
                以及 图像拍摄结果文件夹指定(用于调试看结果的，不是重要功能)

        env_preconfig() - 用于导入包的路径之类的东西

        run() - 让机器人正式开始运行的函数
            命令机器人在不同路段进行不同行为；
            此外还命令机器人在进行蔬菜情况判断，并让机器人在遇到不同的蔬菜情况时进行不同的抓取动作

        __monitor() - 机器人通过摄像头采集蔬菜情况的关键函数
            最终会将蔬菜情况的判断结果存入功能部件camera中，由此来进行机器人行为决策

        go_start()、change_track()、go_end() - 在比赛地图上除了可抓取道路以外的其他三个路段的运动命令
            go_start()对应从赛道起点到第一条抓取道路的起点
            change_track()对应从第一条抓取道路的终点到第二条抓取道路的起点
            go_end()对应从第二条抓取道路的终点到赛道终点
        
        补充说明：
            由于机器人不让采用麦克纳姆轮，所以其左右平移靠的是 三角形的轨迹：
                先在静止状态下转个角度，再直走(三角形的斜边)，然后斜边走完之后停下来把原来的角度转回来，最后再直走，完成向量意义上的左右平移(假平移)
            轨迹如：
                中
                |\
                | \
                |  \
                终  起
            不过由于我们并不需要后退，所以只有 起->中 的这段移动

        下列函数用于机器人莫名其妙走偏之后的左右方向走正大概的微调，只管左右方向上的过偏
        __align_monitor() - 采集当前位置两个蔬菜的中心点
        __align_vector_fuzzy() - 由视觉采集的结果，通过计算两个蔬菜的中心点的差值，大致判断机器人当前的位置时过于左偏还是过于右偏或者不偏,
                                    然后直接走上述三角形的斜边（起->中）
        __reset_is_move_and_yawback() - 把__align_vector_fuzzy()没有调回来的角度给调回来（因为走的是斜边，没有把角度调回来）
        __start_reset_is_move_thread() - 启动运行调回角度的线程，因为要实现同时进行 调回角度和机械臂抓取 的命令，故采用多线程的形式

Modules/Camera.py:
    实现视觉部分的关键类
    视觉处理逻辑流程（这也是Robot.__monitor()函数的运作逻辑）：
        先拍摄一张有且只有两个蔬菜的原始图像，再将图像根据 预定好的大致范围 切割成两个ROI(Region of Interest, 感兴趣区域)，
        每个ROI中有一个蔬菜，之后再检查每个ROI图像，并获取该ROI中的蔬菜信息（包括 蔬菜成熟或存在情况、蔬菜在图像上的中心点、蔬菜外接矩形的长宽），
        最后再保证图像质量稳定的情况下判断 蔬菜成熟或存在情况；
        而 蔬菜在图像上的中心点、蔬菜外接矩形的长宽 给用来微调偏移的函数用

    Camera类：
        __init__() - 类初始化
            self.camera_name - 摄像头名
            self.ROIs - 存储当前批拍摄的这张图片进行ROI切割后的左右两个ROI
            self.frame - 存储当前批拍摄的这张图片
            self.i - 图片编号，存图片用来看结果调试用的，不影响主要功能

        shoot() - 拍摄图像
            拍摄结果存入frame里
        screen_cutting() - 将当前批拍摄的这张图片进行ROI切割，获得两个ROI，一个左，一个右，对应左右两个蔬菜的位置
            切割结果存入ROIs里
        check() - 进行蔬菜成熟度和存在与否的判断
            传入需要筛出的颜色（colors是你要保留的颜色的hsv色域，filtered_colors是你要去掉的颜色的hsv色域）
            判断结果保存到ROI类内的成员变量里

        open() - 打开摄像头
        close() - 关闭摄像头
        reboot() - 重启摄像头
        clean_ROIs() - 清除上一轮的ROIs
        show_rois() - 看看本次拍摄的rois以及其颜色过滤结果图像，调试用的

    ROI类：
        Region of Interest，感兴趣区域，如果拍摄的结果有蔬菜，那蔬菜一般都在这个区域内
        ROI的切割区域是手动调参后得到的，即 由main.py中的全局变量rois指定

        check() - 检查当前ROI的蔬菜成熟情况或存在情况；以及配置好后能返回目标蔬菜的外接矩形长宽和其在原始图像上的中心点
            调用了VisionModule/obj_check.py中的obj_check()和color_check()


Modules/VisionModule/obj_check.py:
    存放图像处理核心函数obj_check()和color_check()
    obj_check() - 根据原始图像和输入的颜色色域，返回蔬菜的成熟或存在情况、目标蔬菜在图像上的的中心点坐标、目标蔬菜的外接矩形长宽、颜色过滤后的ROI图像
    color_check() - 跟obj_check()的唯一不同在于其返回结果只有 蔬菜的成熟或存在情况、颜色过滤后的ROI图像

    上述两个函数都用到了ColorHandler，作为颜色处理的方式

Modules/utils/ColorHandler.py:
    ColorHandler类：
        用于进行图像的颜色处理和颜色检测的工具类
        __init__() - 类初始化
            colors - 通过一系列传参，最后保存的是main.py中的全局变量colors
            colorNames - 同上，最后保存的是main.py中的全局变量colorNames
            filtered_colors - 同上，最后保存的是main.py中的全局变量filtered_colors

        filter_color() - 对图像进行颜色过滤
            能用colors筛出想要的颜色，用filtered_colors筛掉不想要的颜色

        detect_color() - 检测给定的点的一个中心区域内的颜色
            注意，其去掉了 纯黑色颜色的计算，防止影响结果
            通过判断计算中心区域内的颜色平均值是否在colors中已有的颜色色域内，从而来判断是什么颜色


Modules/Bridge.py:
    Bridge系列的基本控制形式如下：
        通过串口通信，上位机向子设备发送串口指令并让子设备进行指定行为；
        与此同时，可以通过子设备向上位机发回的子设备当前状态让上位机得知子设备的当前状态，
        接收的过程通过 上位机开一个线程来并发接收子设备的发回信息 实现

    Arm_Bridge类：
        是一个单向类，只有上位机向子设备发送指令的过程，没有接收
        基本运作流程：
            先对机械臂通讯桥进行初始化init()配置和打开串口,
            之后如果想控制机械臂进行指定运动（其实是从某一状态到达新状态），调用arm_cmd函数；
            arm_cmd函数的使用方法如下：
                arm_cmd(two_wrist, two_elbow, lift)
                two_wrist是一个元组，(左腕弯曲与否,右腕弯曲与否)的形式，1表示是，0表示否
                two_elbow同上，(左肘弯曲与否,右肘弯曲与否)的形式，0表示不弯曲，1表示完全弯曲，2表示弯曲一半程度(即不做到完全弯曲)
                lift是一个数值，0表示让机械臂在底部，1表示让机械臂在中间，2表示机械臂在顶部
                如：
                    arm_cmd((1,0),(0,2),1) 表示 左爪/腕抓取，右爪/腕张开，左肘不弯曲，右肘弯曲一半的程度，机械臂处于顶部
                    arm_cmd((0,0),(1,1),2) 表示 左爪/腕张开，右爪/腕张开，左肘完全弯曲，右肘完全弯曲，机械臂处于中间高度
                注意：
                    每运行一次arm_cmd的含义是 向机械臂发送一次指令，至于指令完全被执行（即机械臂完全运动完成）还需要一定的运动时间，
                    故decisions中会有time这个选项，用于指定延时时间，以等待指令被完全执行完毕（因为是单向发送指令所以只能用延时的方式等待，是手调的）
            
    Car_Bridge类：
        部分函数可以用于双向通信
        基本运作流程：
            先对底盘通讯桥进行初始化init()配置和打开串口，
            然后调用Car_Bridge类中的run_thread()，以启动Car_Bridge接收底盘发来的消息的功能（上位机 <- 底盘），至此准备工作完毕。
            之后就能愉快地通过调用类内封装好的指令发送函数来控制底盘的运动和获取底盘状态了。
            运动用的指令函数：
                go_distance() - 单向地发送 走直线 的指令，无接收
                go_distance_atom() - 发送 走直线 的指令，直到小车走了指定的距离，会阻塞所在线程
                yaw_adjustment() - 发送 原地转弯 的指令，直到确定小车转到指定角度，会阻塞所在线程
                move() - 单向地发送 移动 的指令，无接收 - 没用到
                move_atom() - 发送 移动 的指令，直到小车走了指定的横向和纵向距离
                go_sideway() - 发送 假平移 的指令，直到小车通过假平移走了指定的左右横向距离
                go_vector() - 单向地发送 走斜线 的指令，无接收
            获取状态用的函数：
                get_cur_Yaw() - 获取当前底盘的偏角


Modules/SocketClient.py:
    SocketClient类：
        使用流程：
            初始化后调用run_thread()启动socket通信客户端线程；
            在主线程中修改某些标志位，该客户端通信线程读取到特定标志位被修改后就会发送指定消息给到大车，让大车执行特定指令
